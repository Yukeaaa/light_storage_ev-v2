2. P0-1：必须纠正“训练资格”措辞

这是这一轮最重要的治理问题。

当前报告写的是：

“训练资格由后续实验显式过滤：E1 严格主结论 = L1_strict_matched ∧ split in {train,validation,test} ∧ role==main”

前半句说的是训练资格，后半句却包含 test。

代码现在没有真的拿 test 训练，所以当前结果没污染。但这句话如果被后面的 E1/E2 工程师直接照搬，会造成严重风险：

train/validation/test 被一起理解为“可用于建模的数据”。

必须拆成两个完全不同的概念。

建议冻结：

main_evidence_universe:
sample_layer == L1_strict_matched
AND role == main
AND split in {train, validation, test}

这只是说这些数据都属于主证据体系。

真正的模型权限必须是：

fit_eligible:
split == train

model_selection_eligible:
split == validation

final_test_eligible:
split == test

并明确：

test:
只允许一次正式评估
不得选特征
不得选阈值
不得选模型
不得选择支持域规则
不得根据 test 图形回调参数

这个修改要同时进入 split.py docstring 和 E0_Full_split_audit.md。

这是 P0，关闭 #13 前必须修。

3. P0-2：人口冻结现在是“报告检查”，还不是 machine STOP

这是一个典型的“今天没出错，但未来可能静默错”的问题。

我们之前已经明确冻结：

rows = 85877
matched = 40644
static_only = 45233
api_only = 0

当前正式证据确实满足。

但是 _assert_registry_invariants() 目前只检查：

session_id unique；
split 五值；
sample_layer ↔ match_status；
connection_time 非空；
role 枚举；
field_mode 枚举。

它没有硬检查 85,877 / 40,644 / 45,233。

所以假设以后上游 mapping 意外少 300 个文件，只要剩余 session_id 仍唯一，函数仍可能成功输出 85,577 行，然后只是在报告里显示新数字。

这违背冻结 population identity 的含义。

应该增加机器 STOP：

len(reg) == cfg["inputs"]["manifests"]["static_file_index_rows"]
matched == cfg["inputs"]["manifests"]["match_status"]["matched"]
static_only == cfg["inputs"]["manifests"]["match_status"]["static_only"]
api_only == 0

同时：

set(split_registry.session_id)
==
set(field_mode_registry.session_id)

field_mode registry 不能只是也恰好 85,877 行，会话集合本身必须完全相同。

4. P0-3：禁止关键上游 registry 静默 drop_duplicates

当前代码有三个很典型的治理危险：

audit_idx = audit_idx[~audit_idx.index.duplicated()]

以及 API metadata 的：

.drop_duplicates(subset=["sessionID"])

以及 manifest：

mf = mf[~mf.index.duplicated()]

当前数据显然没有因此产生异常，否则 85,877 会话和结果不会完整通过。

但治理逻辑不应该是：

“如果关键输入重复，就静默拿第一条。”

应该是：

这些对象按契约本来就应该唯一；若不唯一则 fail-fast，并报告重复 key。

尤其：

audit.session_id
manifest.logical_path
api_metadata.sessionID

都属于可追溯性关键索引。

建议改成：

if duplicated:
    raise ValueError(...)

而不是自动去重。

这和我们 raw duplicate amendment 的原则是一致的：原始异常可以存在，但解释和消歧必须显式，不能静默。

5. P1：current_only_fallback 绝不能等同于 field_mode=current_only

这里非常容易影响后面的专利证据。

当前代码实际上定义：

Caltech → main
Office → external_only
JPL 2020-06/07 Arroyo → boundary
其余 JPL → current_only_fallback

也就是说，current_only_fallback 是一个粗粒度 evidence role，不是字段模式。

而全量 field_mode 有：

measured_pilot       46173
measured_no_pilot    14119
current_only         25585

所以必须明确：

role=current_only_fallback 不意味着这个 session 真的是 field_mode=current_only。

否则到 R1/E3 时，有人很容易写：

df[df.role == "current_only_fallback"]

然后把 measured/no-pilot 等数据也混入所谓“JPL current-only 证据池”。

正确的 K1 current-only pool 后面至少应该显式包含：

role == current_only_fallback
AND field_mode == current_only
AND frozen_month eligibility
AND K1 原有其他 eligibility

具体最终 eligibility 继续以 R1 冻结协议为准。

建议 E0F-02.1 报告新增：

role × field_mode
role × sample_layer

两个交叉表。

这样后面任何人都不会把 role 和 field modality 混为一谈。

6. P1：不要再写“交叉表证明 role 与 split 相互独立”

目前报告标题是：

role×split 交叉（证明时间位置与角色相互独立）

从代码架构意义上，你想表达的是对的：

但是从统计意义上这句话不成立。

例如 boundary 全部 880 个都落在 test，正因为 boundary 的定义使用 2020-06/07，而 split 也是按时间排序，所以二者天然相关。

建议改成：

role×split 交叉审计（验证 role 作为正交治理字段保存，role 不参与 assign_split 决策）

“orthogonal governance field” ≠ “statistically independent”。

这是措辞问题，不影响结果。
