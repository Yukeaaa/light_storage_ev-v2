二、P0阻断项一：E3滚动历史发生跨会话污染

当前代码为：

g = cyc.groupby(["site", "garage", "session_id"], sort=False)

cyc["actual_prev"] = g["actual"].shift(1)

cyc["actual_rollmax"] = (
    g["actual"].shift(1)
    .rolling(ROLL_CYCLES, min_periods=2)
    .max()
)

cyc["actual_rollq"] = (
    g["actual"].shift(1)
    .rolling(ROLL_CYCLES, min_periods=2)
    .quantile(ROLL_Q)
)

g["actual"].shift(1)完成后已经是普通Series，后续.rolling()不再按session_id分组。因此新会话前几个周期的滚动窗口可能混入上一会话末尾的数据。

例如：

会话A末尾功率：7, 7, 7 kW
会话B刚开始功率：2, 2, 2 kW

当前实现中，会话B最初的滚动上界可能继承会话A的7kW。这会影响：

A3滚动分位；
A4；
historical headroom参考值；
available mask；
候选率和候选能量。
正确写法

至少应使用组内transform：

cyc["actual_rollmax"] = g["actual"].transform(
    lambda s: s.shift(1).rolling(12, min_periods=2).max()
)

cyc["actual_rollq"] = g["actual"].transform(
    lambda s: s.shift(1).rolling(12, min_periods=2).quantile(0.9)
)

但仅作这一修改仍不够，还需解决下一项“只保留活跃周期”的问题。

三、P0阻断项二：“上一周期”实际变成了“上一活跃周期”

当前流程先执行：

cyc["active"] = cyc["active_share"] > 0.5
cyc = cyc[cyc["active"]].copy()

之后才计算shift(1)和滚动历史。

因此：

A2并不是上一连续5分钟周期的实际功率；
它是上一条“仍被判为活跃”的记录；
12个滚动样本也不是最近60分钟；
它可能是最近12个活跃周期，实际跨越数小时。

例如车辆：

10:00  6 kW
10:05  0.1 kW
10:10  0.1 kW
……
11:30  2 kW

过滤非活跃周期后，11:30的“A2上一周期”可能仍是10:00的6kW。由此产生的预算差值并不是上一控制周期预测误差，而是陈旧历史值与当前功率之差。

这很可能是JPL current-only出现以下异常结果的重要原因：

A2候选率40.9%；
A3候选率62.8%；
A3日候选能量占比17.2%。
正确顺序

应改为：

分钟数据
→ 为每个会话补齐连续5分钟时间网格
→ 对全部连接周期聚合
→ 计算shift(1)和最近12个连续周期滚动量
→ 最后使用当前活跃状态作为评价标签

还应增加超时失效规则，例如：

距上一个有效周期 > 5或10分钟
→ actual_prev失效
→ 重新进入冷启动状态

现有扰动测试只把当前功率从3kW提高到4.5kW，扰动前后都仍属于活跃状态，因此没有触发“当前行被过滤掉”的问题。

应增加：

当前周期3kW → 扰动为0.1kW
当前周期3kW → 扰动为NaN
中间缺失3个控制周期
新会话紧接上一会话

四类测试。

四、P0阻断项三：A4的pilot时间语义与报告不一致

报告将A4写成：

min(前一周期 pilot, 滚动0.9分位)

但代码实际使用：

cyc["A4_min_pilot_quantile"] = np.minimum(
    cyc["pilot"],
    cyc["actual_rollq"]
)

这里的pilot是当前5分钟周期内所有分钟pilot的平均值，并没有shift(1)。

需要明确控制决策时刻：

情况A：pilot是周期开始前已下发的指令

可使用周期起点时已知的pilot，但不能使用整个当前周期的平均pilot。

情况B：pilot只是测量到的导引轨迹

应使用上一周期pilot或当前周期第一条已知值，不能使用后续分钟数据。

建议增加：

pilot_at_decision

并明确来源为：

周期起点前最后有效pilot

或者统一使用：

pilot_prev = groupby(...).shift(1)

否则“所有预算代理无当前周期泄漏”的表述仍然过强。

五、P0阻断项四：核心运行段事件按“起点”归类，未在阶段边界切断

E1先检测完整事件，然后将事件起点与分钟表合并：

events = detect_gap_events(labeled, thr)

events = events.merge(
    anchor,
    on=["session_id", "start_utc"]
)

events["event_phase"] = events["phase"]

也就是说，一个事件只根据起点所属阶段分类。

例如：

事件开始：距done 125分钟，属于core
事件结束：距done 20分钟，已经进入tail

整个105分钟事件仍会被统计为core事件，其全部能量和持续时间也都会计入核心运行段。

当前核心事件持续时间P95达到98.6分钟，因此跨越120分钟阶段边界不是可以忽略的理论情况。

正确方法

事件连续段必须在阶段变化时切断：

gap_candidate=True
且 phase=core
→ 单独形成core连续段

phase从core变为mid
→ 原连续段立即终止

建议直接按以下键分组：

session_id + phase

或为每一阶段分别生成mask：

core_mask = gap_candidate & phase.eq(PHASE_CORE)
mid_mask  = gap_candidate & phase.eq(PHASE_MID)
tail_mask = gap_candidate & phase.eq(PHASE_TAIL)

然后重新应用持续时间≥5分钟规则。

在这一步重跑之前，12.1%的核心事件率和489.7kWh核心差值能量还不是最终可信数字。

七、P1问题：所谓“完全相同eligible mask”并未保证会话集合相同

available_mask()目前只检查：

n_budget_proxy >= 1

它能保证同一个池周期被各代理纳入，但不能保证各代理在该周期使用的是同一组会话。

可能出现：

A2可计算会话：车辆1、2、3、4
A4可计算会话：车辆1、2

两者都满足n_budget>=1，却不是严格配对比较。

修正方式

在会话×周期层先求交集：

eligible_all = (
    prox[CAL_PROX]
    .notna()
    .all(axis=1)
)

然后所有代理都在完全相同的：

site + garage + cycle + session_id

集合上计算候选率和候选能量。

相应测试不能只检查n_budget>=1，而应断言各代理参与的session_id集合完全一致。现有测试只验证了前者。

十、P1问题：done推断只标记了推断点之后的数据

add_done_phases()中，推断done后仅对：

应改成对该会话所有分钟赋值：

idx = sub.index
out.loc[idx, "minutes_to_done"] = (
    inferred_done - sub["timestamp_utc"]
).dt.total_seconds() / 60

同时覆盖率应分别报告：

API锚点会话数/占比
推断锚点会话数/占比

十六、对专利方向的最新判断

本轮数据最重要的信息并不是“发现了大量异常车辆”，而是：

pilot/站级预算与车辆短时实际可执行功率之间存在阶段相关偏差，其中大部分发生在接近完成和降流阶段，核心运行段仍存在较低但不可忽略的偏差。

因此当前主轴应进一步收敛为：

主候选D1-P

一种基于充电响应阶段识别与观测支持域约束的短时可执行功率区间生成及光储充站预算修正方法

建议技术链：

pilot、实际功率、连接时长和历史响应
→ 识别稳定充电/降流/暂停/近完成等响应阶段
→ 生成阶段相关的短时可执行功率区间
→ 计算区间可信度和适用域
→ 限制会话预算或将未执行预算返回站级调度
→ 根据下一周期实际响应更新状态

其中：

阶段识别、可执行区间、可信度、预算返回可以继续；
current-only回退适合作为从属模块；
