# 一、我认为现在最大的风险：D3 的 1060 条 recovery 没有想象中那么强

当前 D3 的恢复条件本质上是：

```text
protective_bound(t) = 过去实际功率的滚动 Q95
actual_power(t) >= 0.95 × protective_bound(t)
连续 3 个 cycle
→ PROTECTIVE → NORMAL
```

而 `protective_bound` 本身来自该车辆**之前自己的实际功率**。

这就出现了一个很危险的自洽关系：

> 用“过去实际功率的高分位数”当边界，然后用“现在实际功率仍接近过去实际功率高分位数”作为能力恢复证据。

这当然是因果的，没有未来泄漏；但**因果 ≠ 有辨识力**。

更关键的是，你们自己的单元测试已经无意中暴露了这个问题。

`test_natural_current_only_branch_and_recovery()` 构造的是：

> **整个 session 恒定 5 kW。**

没有控制激励，没有功率变化，没有“车辆响应了新的请求”。

结果：

* 前 5 分钟历史不足；
* 第 6 分钟进入 M3；
* 第 8 分钟就自动 recovery；
* 后面全部进入 NORMAL。

也就是说：

> **一条什么新动作都没响应、只是一直稳定充 5 kW 的序列，就足以被当前 D3 识别为“response-driven recovery”。**

这是目前整个项目里我认为**最应该优先纠偏的问题**。

所以 P2 报告中的：

> `1060 natural recovery traces / 1060 sessions`

是真的，代码也确实产生了这些 trace；但目前最多证明：

> **1060 个真实会话出现过“当前功率持续贴近自身近期历史高水平”的现象。**

还不能证明：

> **1060 个会话出现了足以支持“恢复更高调度权限”的新能力证据。**

两者差别非常大。

# 二、这也是为什么 P2 的 SUCCESS 不能被解读成“技术效果 SUCCESS”

这一点实际上你们的 P2 protocol 自己写得比较克制。

当前 P2 scope 明确是：

> `mechanism_realizability_only`

而不是性能、收益或真实 EMS 控制效果验证。

这一点必须坚持，不能后面写专利材料的时候无意中把它膨胀。

因为现在四个主要指标里：

### M1 = 1.0

M1 验证的是：

> 信息类别是否能够按照冻结 precedence 映射到唯一 boundary mode。

代码事实上就是穷举 16 种布尔组合，然后按照已经定义好的规则查表。

所以 M1=1 本质是：

**状态规则实现正确。**

不是：

**这种信息分类产生了技术收益。**

---

### M2 = 1.0

这个问题更明显。

代码实际上是：

```text
final_delta = clip(requested_delta, L, U)
```

然后指标验证：

```text
final_delta == clip(requested_delta, L, U)
```

那么只要没有软件 bug：

> **M2 理论上就应该等于 1。**

这证明的是 controller conformance，不是技术效果。

---

### M4 = 0

PROTECTIVE 被定义为：

```text
allowed_delta_interval = [-current_budget, 0]
```

因此正向 release 本身就在数学上被禁止。

所以：

> `unsupported_release = 0`

同样主要证明**规则确实被代码执行了**，而不是证明这个规则“比现有控制技术好”。

---

### 真正依赖真实数据的是 M3

也就是 recovery trace。

所以从科学证据权重来看：

> **P2 真正最重要的不是 M1/M2/M4，而是 M3。**

偏偏 M3 现在存在前面讲的“rolling-Q95 自洽恢复”风险。

这就是为什么我不会把目前 P2 判为 filing-ready。

# 三、D2 已经从“纯概念”前进了一步，但仍然是专利最大的法律/技术风险

这一阶段有一个明显进步，我认可：

以前：

> “权限”“允许程度”“保守控制”

确实容易只是抽象 wording。

现在已经具体成：

```text
LOCKED:
    ΔP ∈ [0, 0]

PROTECTIVE:
    ΔP ∈ [-B, 0]

NORMAL:
    ΔP ∈ [-B, max(0, boundary-B)]
```

然后实际对 EMS 请求的 `requested_delta` 进行 clip。

这个结构已经明显更像一个**控制器中的可执行动作约束模块**，而不是一句策略描述。

这一步是对的。

但是问题是：

### 现在的 `requested_delta` 并不来自真正的 EMS。

它由代码根据 session ID 和 cycle index 人工生成：

* budget 是几个固定档位；
* probe 循环取 `-3 / -1.5 / 0 / +1.5 / +3`；
* 和 EV 实际行为相互独立。

也就是说：

> 当前 P2 证明了“如果一个 EMS 发来了这个调整请求，我们的门控器能限制这个请求”。

而没有证明：

> “真实 EMS 中因为采用这个门控器，产生了一个新的、可测的控制技术效果。”

P2 报告对此也明确做了免责声明。

这其实就是现在 D2 最大的专利风险：

**它到底是一个技术控制机制，还是把已有约束控制换成“permission / allowed range”的表述？**

你们自己的 prior-art stress test 已经正确找到了这个危险点。

内部检索认为最高风险近邻是 ACN：

> observation → conservative constraint → scheduling constraint → constraint relaxation。

同时 ChargePoint 已有 history → power limit，Siemens 方向也已有 boundary → optimizer constraint。

因此仓库自己也已经明确：

> 如果 D2 不能变成真正的设备动作边界，而只是“权限”措辞，应该 Project No-Go。

**我赞成这个杀线，而且建议进一步加严。**

# 四、Claim Surgery v2 还有一个很重要的“证据范围 > 实现范围”问题

目前 Claim 1 已经被改造成完整动作链，这比最初版本好很多：

> 信息类别 → 选择边界生成方法 → 生成 EV 功率边界 → 形成预算修正允许区间 → 限制 requested correction → 持续实测 → recovery → 修改允许区间 → 后续执行。

但代码里有一个非常值得注意的问题。

`pipeline.py` 中真正赋 `boundary_value` 的只有：

```python
M1 → injection_value
M3 → protective_bound
```

**M2 没有 numerical `boundary_value`。**

而测试甚至明确写着：

> `M2 是 dispatch-only（无 boundary_value）→ boundary_unavailable`。

这意味着：

### 当前 claim 叙述容易给人的印象是

四种信息类别都会：

> 选择一种边界生成方式 → 形成一个实际 EV power boundary。

但 P2 当前真正完整跑通的是：

* M3 current-only；
* M4 insufficient history；
* M1 是注入 capability replay；
* **M2 实际只是 branch/mode dispatch，没有可执行数值 boundary。**

所以 Claim 1 如果把全部 D1 类别都作为同等成熟的必备链条，我认为**过宽了**。

我的建议是：

> **主权利要求优先围绕 M3/M4 + D2 + D3 收紧。**

capability-rich / pilot-rich 等更宽的信息类别，可以放到从属权利要求或替代实施例。

不要为了让 Claim 1 “看起来覆盖面大”，把没有形成完整 numerical embodiment 的分支硬放进去。

# 五、“保护降级—响应恢复闭环”和实际状态机并不完全一致

这个问题很容易被忽略。

目前 `state_machine.py` 明确规定：

> M3 一旦 recovery，`m3_recovered` 在整个 M3 segment 内单调保持 True。

也就是说：

```text
M3 PROTECTIVE
      ↓
    recovery
      ↓
M3 NORMAL
      ↓
只要仍然是 M3
永远保持 NORMAL
```

后面即使实际功率再也不贴近 boundary：

> **不会重新退回 PROTECTIVE。**

只有：

* mode 改变；
* run reset；
* severe gap；
* history 重新不足

这类情况才可能重新进入默认状态。

因此当前真正实现的是：

> **信息不足导致保护 → 实际响应满足条件后单向恢复。**

而不是严格意义上的：

> **根据响应证据持续降级 ↔ 恢复的闭环权限控制。**

早期 README / tech disclosure 中还残留了更强的“反馈更新支持状态、保护降级和恢复”的叙述。

这需要统一。

否则代理师读文档时，很容易在：

* README；
* disclosure；
* claim tree；
* P2 implementation

之间看到不同的“发明本体”。

我的建议不是现在把双向状态机补出来。

反而应该：

> **按已经验证的东西收缩文字。**

不要为保持早期故事而扩代码。

# 六、我还发现一个 recovery trace 判定代码 bug

`recovery.py` 中：

```python
m4_before = bool(
    (run["info_mode"] == M4).any()
    and
    (run["timestamp_utc"] < recovery_ts).any()
)
```

这实际上只检查了：

1. run 中某处存在 M4；
2. run 中存在 recovery 之前的某一行。

**并没有检查那个 M4 本身发生在 recovery 之前。**

正确逻辑应该类似：

```python
m4_before = (
    (run["info_mode"] == M4)
    & (run["timestamp_utc"] < recovery_ts)
).any()
```

另外 trace 里：

```text
mode_before = M4
state_before = PROTECTIVE
state_after = NORMAL
```

部分字段也是直接硬编码，而不是从 transition 邻域实际读出。

在现在的数据形态下，大部分 M3 run 很可能确实是 M4→M3，所以这个 bug **不一定会改变 1060 的结论**。

但证据链项目不能留下这种逻辑缺口。

应当修。

注意：

> **修 bug ≠ 重跑冻结 formal test。**

formal test 已经 sentinel consumed，这一点继续保持。

可以针对现有 frozen trace 做静态 audit，或者进入新版本协议，而不是偷偷重新计算正式结果。
