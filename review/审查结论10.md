P0-1：E0 baseline 的代码追溯链现在是错的

当前 e0_full_baseline.json 写：

code_sha = 8d7b7c0...

但 E0F-01 的 input_audit.py、baseline.py、测试和实际产物是在后一个提交 2fbc808... 才加入仓库的。两者之间恰好只有这一个提交，而且这个提交新增了整套 E0F-01 实现。

也就是说现在 baseline 表面上在说：

这些结果由 8d7b7c0 代码生成

但 8d7b7c0 实际并不存在这套 E0F-01 代码。

更具体地说，baseline.py 的 _git_commit() 直接取运行时 HEAD；因为你是在代码还没 commit 的工作树上跑完实验后再一起提交，所以它记录了父提交。

而且还有第二层问题：

parent_baseline.commit

也被写成了运行时 HEAD。

它实际上应该指向历史 K0 baseline 自己记录的提交。现有 design_baseline.json 明确记录的是：

41dd1dd038ebce13b28a76c3254f08e61569dabe

所以当前：

parent_baseline.commit = 8d7b7c0
code_sha              = 8d7b7c0

两个不同含义的字段被写成同一个值了。

这个必须修

以后应严格采用：

代码/配置先提交
→ 工作树 clean
→ 用该 code SHA 跑数据
→ 再单独提交结果产物

这样结果提交可以晚一个 commit，但 baseline 中的 code_sha 会准确指向生成这些结果的代码提交。

我建议 baseline.py 再增加一个 git_dirty 检查：正式冻结运行时如果工作树有未提交代码，直接拒绝生成 frozen baseline。

P0-2：当前 STOP 是正确的，但“冻结停止线”的解释需要纠正

这里有一个很重要的治理区别。

S0 真正冻结在 e0_full.yaml 里的原文是：

同一会话存在无法解释的重叠记录

而 D0 uniqueness 写的是：

会话分钟主键无非法重复

Issue #12 最初列出的 E0F-01 stop-lines 里，也没有写：

raw 文件内 timestamp 必须绝对唯一

现在代码里的：

dup_ts_within_file == 0

是 E0F-01 实现时，对“无法解释的重叠记录”做出的更严格实现解释。

因此你这次不能直接删掉这个检查然后宣布 PASS，这一点你处理得对。

但同样也不能说“原始预注册已经明确规定任何 raw timestamp 重复都必须 STOP”，因为原始冻结文本没有这么具体。

现在正确动作应叫：

STOP 后的口径澄清 / gate resolution

而不是“放宽冻结阈值”。

目前的重复分类还不足以做最终 gate decision

当前分类器真正证明的是：

663 行 = 同一 timestamp + 整行逐字节完全相同
30,226 行 = 同一 timestamp + 行内容不同

但是报告把第二类直接称作：

“亚秒采样，可解释”

这个表述目前证据不足。

ACN-Data-Static 的公开 README 只说明第一列为 ISO 8601 timestamp，并没有给出“相同 timestamp 不同值就是亚秒采样”的数据契约。

所以建议把字段名和报告改为：

same_timestamp_distinct_rows
同一记录时间戳、不同观测值

当前最多可以说：

可能来自采集频率高于时间戳记录分辨率、多源落点或日志系统重复时间标记，具体机制未被当前数据证明。

不要直接写“亚秒采样”。

这点很重要，因为 Caltech 有 10,008 个文件属于这种情况。它不是只有 JPL 才存在。

“663 全部是 JPL 空闲 0.0 心跳”还需要机器可验证地固化

没有直接输出：

所以当前代码能证明“663 行逐字节重复”，但不能单凭 frozen summary 证明：

建议把这个结论也自动化。

尤其要注意：“JPL Arroyo Garage”不等于“K1-X boundary 数据”。

K1 冻结的 boundary 只有 2020-06/07；JPL current-only fallback 又是另一套月份。
