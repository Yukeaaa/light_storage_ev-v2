# 一、现在我们实际上要申请的专利方法是什么？

不是：

> “发现 pilot 比实际功率大，然后把剩余功率分给其他车。”

这个说法创新性不够，而且现有技术非常拥挤。

我们真正应该坚持的主轴仍然是：

> **基于充电桩侧可在线观测的导引信息与车辆实际充电响应，识别车辆短时响应状态，生成数据支持的短时可执行功率区间；根据该区间判断当前状态是否处于模型支持域，在支持域内对站级 EV 功率预算实施有界修正，在证据不足或超出支持域时切换至保护型功率边界，并利用后续实际响应进行反馈更新。**

这就是目前 D1-R 的核心。

仓库 README 现在也是这么冻结的：

> 响应状态识别 → 短时可执行功率区间 → 支持域内有界修正 → 支持域外保护回退。

---

## 把它翻成工程流程，就是 7 个步骤

### 1. 读取桩侧在线可观测量

主要是：

* pilot / allowable current；
* 实际电流；
* 实际功率；
* charging state；
* 最近若干分钟历史响应；
* 会话已连接时间；
* 场站当前 EV 总预算。

**不依赖：**

* 真实 SOC；
* BMS 限功率原因；
* 精确剩余电量；
* 精确未来离场时间；
* PCS 内部拒绝原因。

这是我们的一个重要工程优势。

仓库已经明确把 `disconnect_time`、`done_charging_time`、`kWhDelivered` 当作离线标签，禁止作为在线特征。

---

### 2. 判断车辆当前属于什么“响应状态”

例如未来 E1-Full 可以识别：

* 正常跟随；
* 稳态低吸收；
* 衰减；
* pilot 增大后有明显正响应；
* pilot 增大但短期响应弱；
* 状态不确定；
* 数据不足。

这里最关键的是：

**不能因为 `pilot > actual` 就直接说车辆“还能吃多少”。**

目前仓库也严格保持了这个纪律。现有冻结证据只说明：

> Caltech 核心运行阶段确实存在持续 pilot/actual 响应差异，冻结样本事件会话率约 11.9%；但“差值能否被其他车辆吸收”仍属于 D 级未证明假设。

---

### 3. 为每辆车形成一个短时“可执行功率区间”

不是预测一个点：

[
P_{t+1}=6.2\text{ kW}
]

而更接近：

[
P_{i,t+1}\in[\underline P_{i,t+1},\overline P_{i,t+1}]
]

其含义是：

> 根据当前桩侧可见响应状态和历史数据，在未来短控制周期内，有数据支持的车辆实际执行功率范围。

这点非常重要。

**我们的专利重点不是“预测功率”，而是“给控制器一个可执行边界”。**

目前这部分还没有实现。

C-008 当前仍明确登记为 D 级：

> “短时可执行功率区间可生成”——E2 未运行。

---

### 4. 判断这个区间现在能不能信

即 **support domain / 支持域判断**。

例如：

如果当前：

* pilot 有效；
* 最近连续观测足够；
* 无严重 gap；
* 当前状态在训练样本支持范围内；
* 区间校准误差满足要求；

则：

> 允许控制器使用这个区间。

反过来：

* pilot 缺失；
* 新车辆/异常状态；
* 数据不足；
* 超出训练分布；
* 区间过宽；

则：

> **禁止激进使用。**

进入保护模式。

这一步其实是我认为最有专利价值的部分之一。

---

# 二、真正控制动作是什么？

不是直接做复杂多车优化。

而是：

## 原站级控制器

先得到：

[
P^{base}_{EV}
]

例如原 EMS 认为下一周期给 EV 群 300 kW。

传统系统通常进一步按照：

* pilot；
* 额定功率；
* SOC；
* 用户需求；
* 上一周期功率；

分配。

我们的模块插在这里。

---

## 我们给出一个“执行可行边界”

例如综合车辆状态后得到：

[
P^{exec}_{EV}\in[245,268]\text{ kW}
]

那么原来：

> EMS 给了 300 kW EV 预算

我们的模块不是说：

> “车辆肯定只能吃 268 kW。”

而是说：

> **当前数据支持下，不建议继续按 300 kW 假定 EV 可以执行；控制预算应限制在有证据支撑的边界内。**

于是形成：

[
P^{corr}_{EV}
=============

\operatorname{Bound}
(P^{base}*{EV},P^{exec}*{EV})
]

这就是：

> **支持域内有界修正。**

---

# 三、如果证据不足怎么办？

这正是“保护回退”。

例如 JPL 没有可靠 pilot，只看到 actual current。

不能硬运行完整 D1-R。

则退化成：

> 最近实际功率 / persistence / rolling quantile / 简单状态机形成保护边界。

也就是说我们的发明不是：

> “模型永远说了算”。

而是：

> **有证据才使用信息增益，没有证据就自动退回简单可靠控制。**

这也是为什么现在 JPL `current_only_fallback` 很有意义。

它不是失败数据集，而是未来专利实施例中的：

> **field-mode dependent fallback。**

---

# 四、主动把功率重新分给其他车是不是我们的专利？

**可以有，但暂时不要放独立权利要求中心。**

应当把它定义为 D1-A：

> 有充分正 pilot-step 响应证据以后，才允许把释放出来的预算主动分配给其他已证明存在吸收能力的车辆。

原因很简单：

**“少吃的车释放功率 → 给另一辆车”已经非常拥挤。**

例如 CN112829627A 已经根据车辆实际需求动态调整多个充电单元的功率。([谷歌专利][1])

ChargePoint 的专利族甚至直接涉及：

> 分配功率超过车辆所需时释放多余 power modules，使其可重新分配给其他 dispenser。([谷歌专利][2])

所以：

> **“再分配”本身不是我们的创新核心。**

我们的创新必须发生在再分配之前：

> **怎么从桩侧 I/O 响应推断“当前执行边界”；什么时候相信；怎么有界修正；什么时候回退。**

# 七、我又看到一个值得现在处理的 P1：pilot 缺失现在可能被聚合成 0

这里：

```python
pilot_upper_kw_total=("pilot_power_kw", "sum")
```

pandas 对全部 NaN 的普通 `sum()` 会产生 0。

这意味着：

> JPL current-only 场景本来是“pilot 不可观测”，pool table 可能出现 `pilot_upper_kw_total=0`。

语义上：

```text
pilot unavailable
```

和：

```text
pilot genuinely = 0
```

是两回事。

好在你同时保存了：

```text
pilot_coverage
```

所以数据现在没坏。

但我建议在 D0 前把这个语义堵住。

最佳方案：

* `pilot_upper_kw_total` 在全部 pilot missing 时保持 NaN；或
* 增加明确 `pilot_upper_available=false`；
* 下游任何使用 pilot upper 都必须 gate on coverage。

这尤其重要，因为将来 D1-R 正好要依赖“pilot observable / current-only fallback”这个区别。

# 十五、专利独立权利要求应该抓什么？

我现在会优先抓 5 个必要动作：

### A. 获取桩侧导引与实际响应数据

### B. 根据二者的时间响应关系识别响应状态

这是核心之一。

### D. 判断当前是否处于所述区间模型的支持域

这是另一个很重要的区别点。

### E. 根据执行区间修正站级 EV 功率预算；支持域外使用保护边界

这才形成完整控制技术效果。

# 十七、光储充里面“储”和“光”怎么办？

它们应该在更后面的系统级技术效果里出现。

例如最终：

```text
PV / load / grid constraint
        ↓
station optimizer
        ↓
original EV budget
        ↓
【D1-R executable correction】
        ↓
corrected EV budget
        ↓
EVSE charging profiles
        ↓
actual EV response
        ↓
PCC residual
        ↓
BESS compensation
```

如果 E4/E7 最终证明：

> 修正 EV budget 后，PCC residual 下降、BESS 高频补偿减少、PV spill/curtailment 改善，

那就可以形成一个非常漂亮的从属/第二独立系统权利要求。

但目前 C-005/C-006 仍然是 D 级，不能提前宣称。

---

# 十八、落地性怎么样？

这个方向的**落地性其实比创新性更让我有信心。**

原因是它不要求改车。

核心只要求：

```text
EVSE / CSMS
能读实际充电状态
+
能控制 charging limit
```

OCPP 1.6 已经支持 Smart Charging/load balancing 和 charging profiles；OCPP 2.0.1/2.x 又进一步增强了 Smart Charging。Open Charge Alliance 目前仍同时支持 OCPP 1.6、2.0.1 和 2.1。([开放充电联盟][7])

所以从系统接口层面：

> **“CSMS 计算限值 → Charging Station 执行限值”是现实存在的工程路径，不需要发明一整套新协议。**

OCPP 2.0.1 还有正式 Smart Charging certification profile。([开放充电联盟][8])

---

# 十九、最合理的实际部署方式

我建议最终做三级部署模式。

## Mode A：EVSE 本地

最理想。

桩本地直接：

```text
pilot
actual current
power
state
```

做 1~10 秒或更细响应判断。

优点：

* 延迟低；
* 数据完整；
* pilot 最可靠。

---

## Mode B：CSMS / EMS 云边控制

如果厂家能上报：

* offered current；
* actual current；
* actual power；
* status；

再通过 smart charging profile 下发限值。

则算法可以部署在：

> 园区 EMS / charging CSMS。

这是最容易商业化的方式。

---

## Mode C：current-only fallback

如果厂家根本不上报 pilot：

```text
recent actual
+ current
+ charging state
```

只运行保护模式。

这正好与我们 JPL current-only 的路线对应。

---

# 二十、落地最大的风险不是算法，而是“桩能不能给你需要的 telemetry”

这应该尽早去验证。

不同厂家的后台可能只给：

* actual current；

有的给：

* offered current；
* pilot；
* power；
* charging state；

有的采样周期甚至是：

* 1 min；
* 15 s；
* 5 s。

所以未来专利实施例最好设计成：

```text
Level 1: pilot + actual
Level 2: allowable current + actual
Level 3: current-only fallback
```

而不是强依赖 ACN 的字段名称。

这样可落地性会高很多。

---

# 二十一、还有一个非常有利的点：我们不要求真实 SOC

很多现有控制专利明显依赖：

* SOC；
* battery capacity；
* vehicle request；
* departure time。

例如 CN109361245B 的调配就使用 SOC 和 charging duration。([谷歌专利][9])

CN119261650B 也结合车辆 battery state 调整 charging power。([谷歌专利][10])

如果我们最终能证明：

> **没有车端 SOC/BMS 数据，仍能根据桩侧响应构造有效执行边界。**

这既是一个很好的工程卖点，也是一个非常值得进入说明书的问题定义。

---

# 二十二、但是现在还不能宣布专利 Go

真正决定生死的是下面三个实验。

## Kill Gate 1：E1-Full positive pilot step

必须证明：

> pilot 提高以后，有些状态车辆真的会表现出稳定、可区分的增量响应。

如果完全区分不了：

**主动增配 D1-A 直接砍。**

保留：

> D1-P 保护型预算修正。

---

## Kill Gate 2：E2

我们的方法必须打赢：

* last actual；
* persistence；
* rolling median；
* rolling quantile；
* simple state machine。

关键不是 MAE 小 2%。

而是：

> **区间校准、over-estimation risk、控制可用性有实质改善。**

如果复杂方法只是：

```text
MAE 5.2 → 5.0
```

没有专利意义。

**No-Go。**

---

## Kill Gate 3：E4

必须证明：

> 使用执行边界修正预算以后，控制系统确实更好。

至少出现一个真实技术效果：

* over-allocation 降低；
* residual 降低；
* delivery 不恶化；
* action rate 可接受；
* BESS residual compensation 降低；
* 或同一站功率预算执行精度提高。

否则：

> “区间预测模型”最多是一篇算法，未必值得做控制专利。

# 最关键的一句话

这个项目现在**没有走偏**。

而且与之前容易出现的“做了很多算法，最后发现没有专利必要性”的路线相比，现在最大的进步恰恰是：

> **我们先证明真实问题、先冻结最强简单基线、先建立测试隔离，再允许核心算法出现。**

目前最值得守住的发明主线不是“智能调度”，也不是“功率重分配”，而是：

> **在无法获得车辆真实 SOC/BMS 内部限制的情况下，利用充电桩可观测的导引—实际响应关系，将车辆短时执行不确定性显式转换为控制器可使用的功率区间，并通过支持域判定控制该区间何时可用，在不可靠时自动退回保护边界。**

**如果 E1-Full + E2 能把这句话实验上做实，我认为这就是一个值得继续投入、且具备较好工程落地性的专利方向。**
