这样背景事实和研究假设完全分开。

四、P1-3：时间切分还缺一个真正的确定性细节

当前：

g = g.sort_values("connection_time")

只有一个排序键。

如果两个 session 恰好拥有完全相同的 connection_time，排序结果可能取决于原始输入顺序。

你现在的：

test_split_ignores_insertion_order

没有发现它，是因为合成数据的 connection time 每10分钟一个，没有并列时间。

应改成
g = g.sort_values(
    ["connection_time", "session_id"],
    kind="mergesort",
)

至少用：

connection_time
→ session_id

作为确定性 tie-break。

然后增加测试：

两个或多个 session connection_time 完全相同
→ 输入顺序随机打乱
→ split 仍完全相同

这是 D0 determinism=true 真正需要的。

五、P1-4：connection_time 的数据来源需要再冻结

当前配置写的是：

connection_time = 会话首条记录 timestamp_utc

这里我建议现在就改。

因为对于 matched 会话，我们本身有 API 会话元数据中的真实 connection time。第一条静态时序记录可能因为：

文件起始截断；
采样缺失；
数据导出方式；

晚于真正连接时刻。

既然时间 split 是整个 E0 防泄漏体系的基础，就不应默认用“首条观测”替代会话连接时间。

推荐冻结规则
matched:
    API connectionTime 为 canonical connection_time

API connectionTime 缺失:
    首条有效 timestamp_utc 为 fallback

static_only:
    首条有效 timestamp_utc
    connection_time_source = first_observation_fallback

并在 registry 增加：

connection_time_source

例如：

api_metadata
first_observation_fallback

这样以后发现数据异常时，可以审计某个 split 是根据什么时间产生的。

这项我认为应该在2GB数据正式切分前冻结。

六、P1-5：证据台账还不够“可追溯”

你之前特别强调：

背景和问题必须真实，要有依据可循。

这一点我非常赞同。

但当前：

C-001 source =
充电协议/标准（IEC 61851 语义）

C-002 source =
公开实测/论文 + 协议

还是“来源类别”，不是“可回查来源”。

目前公开依据实际上是可以精确落地的。

例如，INL 官方 ChargeX 已正式列出 2025 年 10 月的 Plug-In Electric Vehicle Charging Response Characterization for Grid Integration。

Caltech 的 ACN 正式论文也明确把 non-ideal battery charging behavior 和 quantized control signals 列为真实充电系统工程挑战。

建议

不用把 CSV 做复杂，增加一个：

source_ref

或者单独建立：

docs/evidence/sources.md

例如：

S-001  IEC 61851 / SAE J1772 control-pilot semantics
S-002  INL ChargeX, Plug-In Electric Vehicle Charging Response
       Characterization for Grid Integration, Oct 2025
S-003  Lee et al., Adaptive Charging Networks, IEEE,
       DOI/CaltechAUTHORS ID

       DOI 10.1109/SmartGridComm.2018.8587550

然后 CSV 写：

C-001 → S-001,S-002
C-002 → S-002
...

这样以后写专利交底书时，不需要再重新寻找“这句话到底哪篇文章证明的”。
