# 二、实际代码中的 M2 到底做了什么

当前核心没有复杂模型。

对于某个自然正 pilot 变化事件，在时刻 `t`：

```text
actual_before = t-1 时刻实际充电功率

pilot_after = t 时刻新的桩侧允许功率

Q95_before = t 之前历史 actual 的滚动95%分位
```

Candidate：

[
P_{\text{allowed-up}}
=====================

\max\left[
\min(P_{\text{pilot-after}},P_{\text{history-Q95}})
-P_{\text{actual-before}},
0
\right]
]

也就是：

> **桩当前允许你到多少是一道上限，车辆最近实际达到过多少又是一道上限；增加功率时同时满足两道限制。**

代码单测甚至明确验证：

```text
C = min(B1 pilot-only, B2 rolling-Q95)
```

所以它不是“智能预测器”。

它本质上是一个：

> **双重上调幅度限制器。**

这是理解本专利的第一关键点。

# 三、D2 的结果是目前整个项目最有价值的一组证据

train+validation：

| 方法          |     Over |    Under |   Coverage |
| ----------- | -------: | -------: | ---------: |
| pilot-only  |    14865 |     2048 |     76.40% |
| rolling-Q95 |     5338 |     4961 |     42.84% |
| Candidate   | **3732** | **5446** | **37.25%** |

Candidate 相比最强简单 baseline：

```text
Over ↓ 30.08%
CoverageRatio = 86.95%
session-equal Over ↓ 37.10%
```

而未见 test 中：

```text
B2 Over = 2477.79
C  Over = 1495.26

Over ↓ 39.65%

Coverage:
B2 = 33.97%
C  = 26.48%

CoverageRatio = 77.97%

session-equal improvement = 44.8%
```

这说明一个很重要的问题：

> **test 并不是所有指标都“更强”。**

它在“减少过度上调”这一侧更强：

```text
30% → 40%
```

但是保守性代价也更明显：

```text
CoverageRatio
87% → 78%
```

Under 同样进一步增加。

所以最准确的结论不是：

> “test证明算法更准了。”

而应该是：

> **在未参与规则确定的数据上，该双重限制仍稳定地减少未经后续实际响应支持的上调量，同时维持相当比例的真实上调机会；其代价是更保守。**

这句话非常适合进入专利实验部分。

# 四、还有一个非常重要的数据现象：Candidate 没有提高“有没有上调能力”的识别率

train+val：

```text
B2 hit rate = 0.6324
C  hit rate = 0.6324
```

test：

```text

C  = 0.6406
```

这意味着 Candidate 的贡献不是：

> “B2 判断不能涨，但我判断能涨。”

而是：

> **二者基本在相同的事件里认为“可以涨”，但 Candidate 给出的允许增加幅度更小。**

因此以后专利绝对不要写：

* 识别车辆上调能力；
* 判断车辆能否吸收；
* 预测车辆最大充电功率；
* 精准判断可用灵活性。

应该写：

> **限制本周期允许增加的功率幅度。**

这会准确很多。

# 五、当前最需要处理的问题：我在 D3 代码里发现一个系统闭环缺口

这个问题比较重要。

D3 代码定义：

```python
park_requested = delta_pilot_kw
```

含义明确：

> 园区 EMS 这一轮希望 EV 增加多少。

然后：

```python
ev_accepted =
    compute_arm_allowed_up(...)
```

但是 `system_arms.py` 里：

```text
S2 =
max(Q95 - actual, 0)

S3 =
max(min(pilot, Q95) - actual, 0)
```

**没有再和 `park_requested` 取最小值。**

---

# 六、这为什么是问题

在真实 EMS 逻辑里必须满足：

[
\Delta P_{\text{EV,actual}}
\leq
\Delta P_{\text{EMS,request}}
]

也就是说：

> EMS 只要求 EV 增加 2 kW，控制器不能最后安排 EV 增加 4 kW。

但当前代码可能出现：

```text
园区请求：
+1 kW

S2计算“车辆最多还能增加”：
+3 kW

当前D3代码：
ev_accepted = 3 kW
```

这在系统语义上是不成立的。

正确应该是：

```text
ev_accepted =
min(
    park_requested,
    vehicle_allowed_up
)
```

---

# 七、当前单测甚至能看出这个问题

D3 单测中有一个例子：

```text
actual = 4
Q95 = 9

S2 allowed_up = 5
```

但同一个事件：

```text
delta_pilot = 3
```

也就是园区定义的 request 只有 3。

当前代码仍然让：

```text
S2 accepted = 5
```

然后拿这个 5 去计算 shortfall。

这不是数据问题，而是：

> **系统动作定义漏了一道“不能超过EMS实际请求”的限制。**

# 八、这也解释了一个之前看起来“过于整齐”的现象

D2 train+val：

```text
Over improvement = 30.08%
```

D3 train+val：

```text
unexpected_shortfall improvement = 30.08%
```

完全一样。

test 又是：

```text
D2 Over improvement       = 39.65%
D3 shortfall improvement  = 39.65%
```

也完全一样。

现在看代码就能解释：

D2：

[
Over=
\max(P_{allowed}-P_{support},0)
]

D3：

[
Shortfall=
\max(P_{accepted}-P_{observed-support},0)
]

而当前：

```text
P_accepted = P_allowed
P_observed_support = P_support
```

因此：

> **D3 shortfall 实际就是 D2 Over 原样搬过去。**

也就是说 D3 当前真正验证的是：

> “如果把 D2 的 Over 当作园区执行缺口，这个缺口再如何被 BESS/PCC 截断。”

而没有真正验证：

> “EMS 的请求量经过车辆允许量限制后，系统实际会怎样。”

# 十、会影响什么？

会影响现在这两类表述：

> “BESS 临时补偿下降 15.27%。”

以及 test：

> “BESS 临时补偿下降 41.41%。”

因为 BESS 的输入就是上面的 `unexpected_shortfall`。

而且由于：

```text
S2 allowed >= S3 allowed
```

通常 S2 比 S3 更容易超过真实 EMS request。

因此加入：

```text
accepted = min(request, allowed)
```

以后，S2 被截掉的量可能更多。

所以：

> **S3 相对 S2 的当前系统收益很可能下降。**

会下降多少，甚至是否还能过 10% 门，现在不能猜。

必须重算。

# 十六、当前 M2 的最大优点

重新看完代码和数据以后，我认为它有五个比较明显的优势。

### 1. 输入都是可以实际获得的

核心只需要：

```text
当前实际功率
当前充电桩允许功率/电流
之前的实际功率历史
```

没有：

* 真 SOC；
* BMS 内部限功率原因；
* 准确离场时间；
* 未来需求。

这对工程实施非常有利。

---

### 2. 因果时序总体做得比较干净

Q95 使用：

```text
shift(1)
```

即只用当前周期以前的数据。

当前 actual 不参与构造自己的历史上界。

候选公式也没有用：

```text
actual_1min
actual_3min
actual_5min
```

这些只作为结果评价。配置明确冻结了这一点。

---

### 3. strongest simple baseline 从第一天就在

这一次不是：

> “先得到漂亮结果，后来才发现 rolling baseline 很强。”

而是直接比较：

```text
B0 no-up
B1 pilot-only
B2 rolling-Q95
C candidate
```

而且 B2 是固定 strongest baseline。

这是当前证据可信度明显高于旧 D3 的地方。

---

### 4. test 真正复现了

single-exposure test 中仍然：

```text
Over ↓ 39.65%
CoverageRatio 77.97%
session等权方向一致
```

所以至少不能解释成：

> “只是某几个开发月份凑出来的。”

---

### 5. 规则极其简单

```text
允许上调后的功率
不能超过当前桩侧允许上限
也不能超过历史实际响应支持水平
```

计算量、通信量都很低。

这对真实园区 EMS 部署有优势。

# 十七、但这恰恰也是它最大的专利弱点

因为：

[

是非常简单的组合。

审查员完全可能问：

> 既然一个是桩的物理/协议上限，一个是历史响应上限，为安全起见取二者较小值，为什么不是本领域技术人员自然会做的事情？

这是当前**创造性最危险的攻击点**。

而且现有技术的周围已经非常拥挤。

# 十八、当前最危险的现有技术，不只是之前的 ChargePoint

ChargePoint 的 US10464435B2 已经明确公开：收到功率限制请求后，根据充电端口近期实际供电历史确定限制值；其实施方式甚至包括历史平均值或历史最大值。因此，“历史实际功率 → 后续限制”本身不能成为我们的主创新。([Google 专利][1])

ACN 专利族 US11376981B2 更接近我们的数据背景：它使用 pilot 与实际 charging-rate 时序，并专门区分 pilot 是否构成约束，从非绑定 pilot 情况提取车辆最大充电率相关信息，再将拟合模型用于调度。因此“pilot + actual/history 用来理解车辆能力”也已经非常拥挤。([Google 专利][2])

---

# 十九、这次重新检索后，我认为 Schneider 这篇尤其危险

US20180086213A1 / US10230198B2 的方案已经读取：

* 上游 EVSE 的 pilot / maximum offer；
* EV 实际 current draw；
* 系统可用容量；

再动态产生新的充电 offer。

其一个实施方式就是在“系统可分配量”和“上游 EVSE 最大允许值”之间取较小值；另一个实施方式还明确描述，如果车辆实际消耗低于 EMS 给出的 offer，则进一步降低 offer 至实际消费附近。([Google 专利][3])

因此：

> **“pilot + actual + 取较小值”绝对不能单独作为我们的发明中心。**

这是新版 prior-art element map 必须重点攻击的第一篇近邻。

# 二十、园区 EMS → 多桩分配也已经很成熟

US20220153162A1 已公开 EMS 给出可用于 EV 充电的 allowable power，充电控制系统再综合每桩最大功率、当前功率、优先级、预约等生成各桩设置。([Google 专利][4])

因此：

> “园区 EMS 给 EV 总预算，然后分给多个充电桩”

也不能成为区别点。

因此：

> “把 EV 灵活性和 BESS、PV 一起做联合协调”

也不能单独扛创造性。

# 二十二、那当前还剩下什么真正值得保护？

经过这次代码+现有技术双重审查，我认为主 Claim 应该进一步收窄成：

> ## **“园区已有一个 EV 聚合功率上调请求，如何避免把该请求中的过大部分交给车辆。”**

具体技术链：

```text
园区EMS给出：
EV总功率希望增加 ΔP_req
             ↓
对每个正在充电对象取得：
当前actual
当前charger allowable
当前周期以前的actual历史
             ↓
根据历史actual得到
历史响应支持上限
             ↓
该车上调后功率
同时不得超过：
① 当前charger allowable
② 历史响应支持上限
             ↓
得到每辆车最多允许增加多少
             ↓
所有车辆求和
得到EV群最多允许增加 ΔP_EV,max
             ↓
真正采用的EV群增加量：
min(ΔP_req, ΔP_EV,max)
             ↓
再分配到各车辆
```

**这条链是目前最值得做独立 Claim 的版本。**

尤其是这一步：

[
\Delta P_{EV}
=============

\min(
\Delta P_{req},
\sum_i \Delta P_{i,allow}
)
]

现在必须进入 Claim 和修正后的代码。

```text
→ 采用明确能力上限
```

这样证据和 Claim 对得最严。

# 二十五、还有两个代码/实验细节需要写进“已知限制”

### 第一，5min 后 actual 不一定对应“一个严格隔离的 pilot 阶跃”

`pilot_steps.py` 要求后续 +1/+3/+5min：

* 同一个 run；
* actual 有效；

但没有要求：

> `t` 到 `t+5` 期间 pilot 一直保持在 `pilot_after` 不再变化。

所以：

```text
P_support =
max(actual_5min - actual_before, 0)
```

应该解释为：

> **自然 pilot 上调事件后 5 分钟实际观察到的功率增加量。**

不要写成：

> “该单次阶跃造成的严格因果增量。”

由于所有 B1/B2/C 使用完全相同事件集，这并不直接破坏相对比较，但会限制因果表述。

我建议申请前只做一个**非门控诊断**：

```text
统计事件后5min内是否再次发生明显pilot变化
```

可以报告比例。

不要重新筛 test、不要重新定义主指标。

---

### 第二，配置和实际 D2 代码有一个小不一致

配置写：

> 当 `pilot < actual - tolerance` 时应降级 M2。

但当前正式 D2 评价集主要检查：

```text
M2
q95 valid
actual valid
```

并没有在正式 Candidate 评价里执行这条 anomaly downgrade。

因此这条规则：

> **不要作为“已经得到 test 支持的核心步骤”写进 Claim。**

可以：

* 删除于 v3 主 Claim；
* 或仅作为可选数据异常实施方式。

不要为了它重新跑 test。

# 二十六、治理层面也有一个小瑕疵

`test_runner.py` 的文字纪律明确写：

```text
single-exposure
禁止重复
```

并且 test 只在 D3 GO 后运行。

但代码层没有类似旧 P2 sentinel 的永久锁。

换句话说：

> 技术上仍然可以再次调用 runner。

另外，`test_policy` 和 TEST_PASS 结果是在同一个 commit `48b5205` 里提交的，而不是先有一个独立 Git commit 证明 policy 已冻结，再有结果 commit。该 commit 本身同时记录了冻结规则和 test 结果。

这不会让数据结果失效。

但从审计严格度看：

> **single-exposure 是流程治理事实，不是强代码治理事实。**

考虑当前本来就是 fast-track，我认为可接受。

现在可以补一个：

```text
E7_FAST_TEST_CONSUMED.md
```

明确：

```text
48b5205 = 永久最终test exposure
后续任何运行都不得重新定义为confirmatory test
```

# 三十二、“下降请求有效性”为什么我不建议做第二专利

数据确实很有意思：

```text
negative events = 20,725

5min actual下降中位数 ≈ 0

42.33% 没看到actual下降
```

这说明：

> 降低 pilot 并不代表实际负荷一定会跟着降低。

很适合做工程诊断。

但现有技术已经明确认识到这个物理现象。例如 EP4494922A1 明确说明：若车辆当前实际充电功率本来就低于新的最大充电功率，那么降低最大功率不会产生实际降低效果。([Google 专利][6])

所以单独申请：

> “判断降功率命令是否会生效”

我认为风险很高。

**不值得现在另开项目。**

# 三十三、M3 current-only 也不适合独立申请

这部分现实价值很高。

因为数据里大量情况：

```text
没有pilot
只有actual history
```

原始 V2.0 也明确指出 JPL 有大量 current-only 文件。

但：

> “根据近期历史功率限制后续充电”

正好是 ChargePoint US10464435B2 的核心之一。([Google 专利][1])

因此 M3 最适合：

> **当前主专利的兼容性 fallback。**

不是第二专利。

# 三十四、E5“信息可靠性→控制回退”是唯一值得留档的后续候选

原 V2.0 其实已经设计过：

```text
actual可靠性
pilot可靠性
userInputs可靠性
模型近期误差
        ↓
不同可信度
        ↓
不同约束/回退
```

这一方向与目前主专利有天然延续性。

但当前还缺一个关键证据：

> **动态可信度控制是否相对固定保守规则产生独立系统收益。**

目前没有。

而“confidence/trust → fallback”在控制领域本身又非常普遍。

所以我的建议：

> **列入“下一申请候选观察池”，但现在不启动。**

只有主专利完成以后，如果确实希望做 continuation / 第二件申请，再用 1～2 天做杀伤性 baseline gate。

# 三十五、E6 跨站切换现在更没有必要

原设计规定：


所以没有真实问题触发 E6。

现在再做：

> “跨场站适用度模型”

就是为了找专利造问题。

应该停止。

# 三十六、多车回收重分配继续维持 No-Go

这一块既有此前项目的失败历史，又有大量现有技术。

现在再把：

```text
某车吃不下
→功率给另一辆
```

包装成第二专利，没有必要。

尤其 Schneider 已经通过多个 retrofit coupling 的实际 consumption、system capacity 和 pilot offer 在多车之间协调功率；多端口 EMS 分配本身也已是成熟技术。([Google 专利][3])

# 三十九、申请前我认为真正必须做的只有 5 件事

# 四十、最终总评

现在这件专利的价值并不在于它“算法高级”。

恰恰相反：

> **算法很简单、变量全可观测、真实数据量大、强 baseline 已比较、未见数据复现、技术问题能解释。**

这是它最大的优点。

最大的弱点则是：

> **“pilot 上限 + 历史上限 → 取更小值”本身非常容易被认定为已知约束的常规组合。**

因此专利成败取决于我们能否把保护点严格落在：

> **“园区 EMS 已经提出 EV 聚合上调需求以后，先利用充电桩当前允许值和车辆历史实际响应共同得到各车辆可接受的上调量，再汇总限制本周期真正交给 EV 群的调整量，而不是把园区要求直接当成车辆可执行量。”**

这条具体控制链。

**我的最终项目评价是：主方向继续，其他方向暂不并行；先完成 D3 纠错审计。当前最值得投入的已经不是更多实验，而是把代码—证据—Claim—现有技术四者真正对齐。**

另外，这次审查发现的 D3 request-cap 问题我认为应该列为 **P0 阻塞项**：在它解决前，我不建议把当前“BESS 临时补偿降低 15%/41%”写入正式技术交底书的已验证效果表。D2 的 30%/40% Over 改善则可以继续作为当前核心数据证据。
