# 二、最终要验证的专利方案，先用最具体的话说清楚

不要再用“投影”“权限”等词。

整个方案就是：

```text
① 园区读取：
   光伏出力
   园区基础负荷
   储能当前可充/可放功率
   变压器/PCC限制
   当前EV总充电功率

             ↓

② 园区EMS算出：
   “这一轮希望EV总功率增加多少/降低多少”

             ↓

③ 对当前每辆正在充电的车读取：
   实际充电功率
   充电桩允许功率/电流（有则用）
   历史实际充电功率
   明确车辆能力信息（有则用）

             ↓

④ 根据当前能拿到哪些信息，
   对每辆车分别确定：
   “最多可以增加多少”
   “最多可以降低多少”

             ↓

⑤ 汇总所有车辆：
   EV群最多增加多少
   EV群最多降低多少

             ↓

⑥ EMS想调的量如果超范围：
   按车辆实际允许范围限制

             ↓

⑦ EV承担能够承担的部分

             ↓

⑧ 剩余部分由BESS补偿；
   BESS也不足时反映到PCC/变压器约束

             ↓

⑨ 下一控制周期重新读取最新状态
```

这就是后续所有实验、代码和专利文字的统一主线。

| 数据             | 来源                       | Evidence         | 当前情况  | 是否关键     |

| BMS/车辆明确最大能力   | ACN没有                    | 缺失               | 无     | 只做可选实施例  |

# 五、D0-2：自然 pilot 变化事件库

这是整个加速方案中**最重要的数据工作**。

目的不是预测。

而是寻找真实历史中：

```text
充电桩允许功率发生改变
        ↓
车辆实际功率真实怎么变化
```

这样我们才有真实依据判断：

> EMS 想增加/降低 EV 功率以后，车辆到底有没有可能执行。

---

## 主事件规则

建议冻结一套，不反复调。

### 正向事件

pilot 增加：

```text
Δpilot >= 2 A
并且
Δpilot / pilot_before >= 15%
```

### 负向事件

pilot 降低：

```text
Δpilot <= -2 A
并且
|Δpilot| / pilot_before >= 15%
```

### 前置稳定

事件前至少 3 分钟：

* pilot 无明显第二次变化；
* actual 非缺失；
* actual 没有剧烈跳变。

### 后置观察

至少保留：

```text
1 min
3 min
5 min
```

实际响应。

### 排除

* 接入后最初 5 min；
* severe gap；
* 数据损坏；
* 明显非物理功率；
* offline 评价时可排除 doneCharging 附近 10 min；
* 但 doneCharging/disconnect **绝不能作为在线特征**。

## 正 pilot 上调事件

### A级：足以支持主动增加功率实验

建议至少：

```text

stations >= 5

```

### B级：可以做，但专利要收窄


或者明显集中在少数桩/月。

这时：


只保留：

* 明确 capability 时可以增加；
* 信息不足时限制增加；

不再花时间找其他统计特征救它。

# 九、最终四种处理方式建议

## M1：有明确车辆能力信息

例如：

```text
车辆/BMS允许最大功率 = P_cap
```

则：

```text
最多增加 = max(P_cap - 当前预算, 0)
最多降低 = 当前预算
```

但：

> ACN 没有真实 M1 数据。

所以 M1：

**保留为从属权利要求/可选实施例，不进主实验 Go 门。**

# 十、M2：有 pilot + actual + 足够历史

这是本轮需要补实的模式。

建议一个极其简单的上限：

[
P_{upper}
=========

\max\left(
P_{actual},
\min(P_{pilot},Q95_{history})
\right)
]

翻译成工程话：

> 本周期不允许把车辆功率增加到“当前 pilot 允许值”和“之前实际达到过的高功率水平”两者中较大的幻想值，而只取两者中较小者；同时不能低于车辆当前已经实际运行的功率。

例如：

```text
当前 actual = 4.0 kW
pilot允许 = 7.2 kW
过去15min实际Q95 = 5.6 kW

→ 上限 = 5.6 kW
→ 当前最多增加 1.6 kW
```

而不是：

```text
pilot - actual = 3.2 kW
→ 全部当作可增加能力
```

历史 Q95 仍只使用**当前以前的数据**。旧 boundary 实现已经采用 `shift(1)` + 15min Q95，避免当前值参与构造自己的历史边界。

### 数据异常处理

如果：

```text
pilot 缺失
pilot < actual - tolerance
history不足
```

不要硬计算 M2。

直接降级。

---

# 十一、M3：只有 actual + 足够历史

这里不要再碰失败的 D3。

建议直接：

```text
最多增加 = 0
最多降低 = 当前EV预算
```

也就是说：

> **没有 pilot / capability 支撑时，本周期不允许 EMS 主动增加这辆车的预算，但允许降低。**

这其实正好对应旧 P2 默认的 `PROTECTIVE / SHRINK_ONLY`：

```text
[-current_budget, 0]
```

以前 D3 的作用是后来恢复正向增加。

现在：

> **永远不做 D3 恢复。**

如果以后真的重新拿到了 pilot/capability：

```text
信息类别自然变成 M2/M1
```

才重新允许增加。

这个解释比 Q95 recovery 清楚得多。

---

# 十二、M4：历史不足

建议完全沿用旧机制：

```text
最多增加 = 0
最多降低 = 0
```

即：

> 本控制周期保持原 EV 预算不变。

旧 P2 已经实现了 M4 的 fail-closed `[0,0]`。

例如刚插枪：

```text
只有1–2分钟数据
```

不急着告诉 EMS：

> “这辆车还有很大灵活性。”

等数据够了再进入其他模式。

---

# 十三、最终的信息处理规则就非常简单

| 当前信息                     | EMS 对这辆车能做什么              |
| ------------------------ | ------------------------- |
| 明确车辆能力存在                 | 可在能力范围内增加/降低              |
| pilot + actual + history | 在 pilot 和真实历史共同支撑范围内增加/降低 |
| actual + history，没 pilot | **只能降低，不允许增加**            |
| history不足                | **本周期保持**                 |

这个规则本身就是后续工程实现的核心。

# 十四、阶段 D2：真实 EV 数据验证

这里先不放 PV/BESS。

只回答：

## D2-1 M2 上调能力验证

对每一个真实 positive pilot step：

事件前计算：

```text
Candidate允许增加多少
```

然后事件后有真实：

```text
actual到底增加了多少
```

定义：

[
P_{support}
===========

\max(P_{actual,5min}-P_{actual,before},0)
]

这个是：

> 在这个真实自然事件中观察到的实际增加量。

不是车辆理论最大能力。

# 十五、必须放的简单 baseline

建议只放三个。

### B0：完全不增加

```text
allowed_up = 0
```

最保守。

---

### B1：pilot-only

```text
allowed_up =
max(pilot - actual, 0)
```

最容易犯“把 pilot 当能力”的错误。

---

### B2：rolling Q95

```text
allowed_up =
max(Q95_history - actual, 0)
```

**这就是最重要的强简单 baseline。**

上一轮已经证明 rolling 类方法很强，所以必须第一天放进去。

---

### C：候选 M2

```text
allowed_up =
max(
  max(actual, min(pilot,Q95_history))
  - actual,
  0
)
```

---

# 十六、D2 只看四个指标

### 1. 超过真实观察支持量

[
Over =
\max(P_{allowed}-P_{support},0)
]

越小越好。

这代表：

> 算法允许增加的量，比这次真实事件中车辆实际增加的还多多少。

---

### 2. 没利用到的真实响应

[
Under =
\max(P_{support}-P_{allowed},0)
]

越小越不保守。

---

### 3. 有效上调命中率

candidate 说：

```text
可以增加 >0
```

而真实后续：

```text
确实增加
```

的比例。

---

### 4. 覆盖率

不能靠：

```text
99%时间都说不允许增加
```

得到“高准确率”。

所以必须报告：

> candidate 实际放行了多少真实上调机会。

# 二十、正向真实事件怎么嵌入“光储充”

假设真实 ACN 事件：

```text
pilot:
5 kW → 8 kW

真实actual:
5 kW → 6.2 kW
```

说明在这个真实事件中：

```text
实际观察支持增加量 = 1.2 kW
```

构造园区场景：

```text
PV突然富余 3 kW
```

园区 EMS 因此希望：

```text
EV +3 kW
```

比较不同控制器。

### B1 pilot-only

可能允许：

```text
+3 kW
```

但真实观察：

```text
只增加1.2
```

于是：

```text
1.8 kW需要BESS继续吸收
或形成PCC偏差
```

### Candidate

如果判断最多：

```text
+1.5 kW
```

那么实际不可执行部分明显减少。

---

# 二十一、负向事件怎么嵌入园区

真实 ACN：

```text
pilot下降 3 kW
actual实际下降 2.5 kW
```

园区构造：

```text
生产负荷突然增加
变压器接近上限

EMS希望：
EV -3 kW
```

于是可以真实评价：

> EV削减没有完全达到计划时，剩下多少需要 BESS 放电。

---

# 二十二、这里使用一个非常重要的“禁止外推”规则

不构建：

```text
神奇EV响应仿真器
```

而直接定义：

> 在真实 pilot 事件中观察到的实际变化量，是本事件可以验证的实际响应支持量。

如果 candidate 允许的调整量小于等于这个真实观察量：

> 可认为没有超出该事件已经观察到的响应支持。

如果 candidate 要求更大：

> 超出部分视为未被此次真实观察支持。

这样不需要声称：

> “我们知道车辆真正最大功率。”

---

# 二十三、园区 BESS 怎么建

只需要普通物理模型。

定义：

```text
E_BESS
P_charge_max
P_discharge_max
SOC_min
SOC_max
eta_charge
eta_discharge
```

建议不要固定一个绝对容量，按 EV 池峰值缩放做三档：

```text
BESS power =
0.25 × EV peak
0.50 × EV peak
1.00 × EV peak
```

容量统一采用例如：

```text
2 h × BESS rated power
```

初始 SOC：

```text
20%
50%
80%
```

这样能覆盖：

* 几乎不能放；
* 正常；
* 几乎不能继续充；

三类情景。

`XiTongJueCe` 中 BESS 的 SOC、功率、效率和普通 EMS 建模参数可作为工程范围依据。

# 二十五、园区 EMS 用最简单规则

不要 MPC。

定义：

当前：

[
P_{grid}
========

P_{base}+P_{EV}-P_{PV}
]

先不算 BESS 动态补偿。

---

## 如果超过变压器限制

比如：

```text
P_grid = 820 kW
P_limit = 750 kW
```

那么 EMS 希望：

```text
EV减少70 kW
```

---

## 如果禁止反送并出现 PV 富余

例如：

```text
P_grid = -50 kW
```

那么 EMS 希望：

```text
EV增加50 kW
```

---

## 如果在允许范围内

```text
EV adjustment = 0
```

这就是整个 EMS。

越简单越好。

因为：

> 我们不要让审查人怀疑效果来自一个复杂优化器。

# 二十六、EV群怎么汇总

假设当前有三辆车。

```text
A：最多 +4 / -7
B：最多 +2 / -6
C：最多 +0 / -5
```

则：

```text
EV群最多增加 = 6 kW
EV群最多降低 = 18 kW
```

园区 EMS 要：

```text
+10 kW
```

最终：

```text
EV只增加6 kW
```

剩余：

```text
4 kW
```

交给 BESS。

BESS如果只能再吸收 3：

```text
1 kW
```

留到 PCC。

### Step 7

园区希望的 EV 调整量超过该范围时：

按限制后的 EV 总功率在充电对象之间执行分配。

### Step 9

对于 EV 未承担的剩余功率调整量：

> 根据 BESS 当前可充/可放能力进行补偿；仍无法补偿的部分反映至电网接口。

### Step 10

下一控制周期重新获取最新状态并重复。

## 我对当前方案最核心的建议

现在不要把目标定成：

> “证明一个很先进的光储充算法。”

而应该锁死成：

> **证明一个非常具体的控制接口问题：园区系统根据光伏、负荷、储能和电网状态希望改变 EV 总功率时，不能默认所有车辆都能完成这个调整；系统先根据各车辆当前真实可获得的信息确定允许增加/降低的范围，再限制本次 EV 功率调整，剩余功率由储能和电网平衡。**

数据方面则坚持：

> **车辆响应是证据核心，必须尽可能真实；光伏/负荷/BESS/PCC是系统传播环境，可以透明混合建模。**

这条路线最大限度保留了前期已经完成的 D1、D2、ACN 数据工程和 P2 代码，同时把已经死亡的 D3 完全切掉；而且第一轮只需要做**数据门 + 真实 pilot event 验证**，在系统模拟投入之前就能再次把方向快速杀一次，避免重复前 20 天的问题。
