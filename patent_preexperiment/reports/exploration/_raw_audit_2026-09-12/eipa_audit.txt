# EIPA charging-point occupancy dataset (Poland, 23 June – 7 July 2026)

A 14-day reference series of the occupancy state of the public electric-vehicle
charging points reported by the Polish national register of alternative-fuels
infrastructure (EIPA, Ewidencja Infrastruktury Paliw Alternatywnych, operated by
the Office of Technical Inspection, UDT), together with the collector and
analysis code.

An associated journal article is currently under review. A link to it will be
added to this record once it has been published.

Collection window: 2026-06-23 14:43 UTC – 2026-07-07 14:43 UTC
(13 d 23:59:59; nominally 14 days).
Polling cadence: 60 s (the empirically determined native publication cadence of
the source). Coverage: 20,156 scheduled polls, 1 failure; the successful polls
cover 20,155 of the 20,161 minutes of the window (99.97%), longest gap 3 min.
Acquisition used change-triggered delta logging: a row is stored only when a
point's state code or source-side status timestamp changes.

## Files

### transitions.csv.gz (7,230,030 rows; 27,666 distinct point identifiers)

Delta log of observed state records. One row per point per observed change
(plus one baseline row per point at first observation). Of the 7,230,030 rows,
905,427 are genuine state changes, the remainder being records in which only the
source-side timestamp moved.

The count of distinct identifiers exceeds the static snapshot because identifiers
turn over during the window: 13,974 identifiers appeared in the dynamic stream
that were absent from the snapshot, whilst the population size itself remained
stable. Any longitudinal use of the register should account for this.

| column | description |
|---|---|
| ts_utc | UTC wall-clock time at which the collector observed the record (ISO 8601) |
| point_id | charging-point identifier as reported in the EIPA dynamic feed |
| status | combined state code: 1 = free (availability=1, status=1), 2 = busy (availability=1, status=0), 0 = operationally unavailable (availability=0) |
| status_ts | source-reported timestamp of the last status change of this point (ISO 8601, as published in the feed) |

The `status_ts` field is populated for every observed state change, but its tail
is long: within the analytical cohort, 1.50% of changes carry a timestamp older
than one hour and the most extreme is retrospective by 113.2 days. The median
lag between the source timestamp and the instant of observation is 86 s
(interquartile range 69–105 s), with no negative values. Users intending to
re-date transitions from `status_ts` should characterise that tail first.

### poll_log.csv.gz (21,239 rows)

Per-poll audit log enabling completeness verification. Phase 1 contributes
1,083 rows, phase 2 contributes 20,156.

| column | description |
|---|---|
| ts_utc | UTC time of the poll |
| phase | 1 = calibration phase (18–20 s polling, 6 h), 2 = reference phase (60 s polling, 14 days) |
| ok | 1 = poll succeeded, 0 = failed |
| n_points | number of points present in the dynamic feed at this poll |
| n_changes | number of rows written to the delta log at this poll |
| free / busy / unavail | counts of points by combined state code |
| src_ts | publication timestamp of the feed ("generated") |
| error | error message for failed polls, empty otherwise |

### calib.csv.gz (1,083 rows)

High-frequency samples from the calibration phase, used to determine the native
publication cadence of the source. The 361 observed changes of the publication
timestamp give a median interval of 60 s (5th–95th percentile 59–61 s, extremes
37–72 s). Querying more frequently than once per minute therefore returns
snapshots that the source has not yet refreshed.

| column | description |
|---|---|
| wall_utc | UTC time of the sample |
| src_ts | publication timestamp of the feed at this sample |
| payload_hash | hash of the dynamic-feed payload (detects unchanged snapshots) |
| free / busy / unavailable / total | counts of points by state |

### points_meta.csv.gz (13,928 rows)

Static snapshot of point metadata taken at the start of the observation window.

| column | description |
|---|---|
| point_id | charging-point identifier (joins to transitions.csv) |
| station_id | identifier of the parent charging station |
| max_power | maximum power over the point's connectors [kW]; missing for 699 records |
| interfaces | pipe-joined connector interface codes as published by the register |
| modes | pipe-joined charging-solution mode codes as published by the register |

Power-class assignment used in the analysis: DC for max_power >= 50 kW, AC for
max_power < 50 kW. Connector interface codes 11, 29 and 30 denote DC couplers;
codes 10, 17 and 18 denote AC couplers. The band above 22 kW and below 50 kW
contains 465 points, of which 268 carry DC connector codes; sessions at those
points account for 3.6% of the total, so the choice of threshold within that
band does not materially affect aggregate results.

Population balance: of the 13,928 snapshot records, 13,229 carry a power
specification and 236 never reported a status during the window. Of those 236,
61 carry a power specification and 175 do not. Intersecting the snapshot with
the points reporting status yields the analytical cohort of 13,168 points
(7,499 AC and 5,669 DC) used throughout the analysis.

## Code

- `controller.py` — two-phase acquisition automaton (cron-driven, 1-min tick):
  phase 1 source characterisation, phase 2 reference acquisition with delta
  logging and audit log; SQLite storage. The feed endpoint is read from the
  `EIPA_DYNAMIC_URL` environment variable and is not hard-coded.
- `status.py` — collection health monitor.
- `export_csv.py` — consistent snapshot export of the SQLite databases to the
  CSV files above.
- `reproduce.py` — end-to-end reproduction of all tables, figure series and
  headline numbers of the analysis from the four CSV files (pandas + numpy;
  approximately 1.5 GB RAM; approximately 60 min on one core).
